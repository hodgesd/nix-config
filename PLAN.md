## Build (all declarative in this repo unless noted)

### Vault MCP server on the mini
`hosts/darwin/mini/vault-mcp/server.py` — same lean-fastmcp shape as
Phase 2, purpose tools only:
- `append_inbox(text, title?)` → `Inbox/YYYY-MM-DD HHMM <slug>.md`
  (create-only, never overwrites)
- `create_daily_note(date?)` → from the daily template, idempotent
  (exists → returns "already exists", never clobbers)
- `read_note(path)`, `search_notes(query, folder?)`, `list_notes(folder)`
- **No delete, no arbitrary write, no overwrite.** Deny at the server
  layer regardless of path-jail: `.obsidian/`, `.git/`, any dotfile,
  symlinks (resolved paths must stay under the vault root), binaries.
  Path jail = resolve + prefix check on every access, plus launchd-level
  confinement of the process to the vault path where practical.
- Bind `127.0.0.1:9102`; launchd **user agent** (iCloud files belong to
  your session — same reason the darwin compose-stack module is a user
  agent), python env from nixpkgs, RunAtLoad + KeepAlive.
- Bearer token, generated by you into `secrets/mini.yaml`
  (sops pattern already live on the mini for the Kuma NAS creds).

### Exposure + hermes wiring
- `tailscale serve` on the mini: HTTPS `:8321` → `127.0.0.1:9102`
  (the port the Phase-0 ACL draft reserved). One-time command,
  documented in the phase doc.
- **hermes-egress change (VM):** allow `100.122.244.86` (mini) tcp/8321
  *before* the CGNAT reject — the first deliberate east-west hole, one
  destination, one port, commented.
- `services.hermes-agent.mcpServers.vault = { url = "https://mini.jaguar-duckbill.ts.net:8321/mcp/"; tools.include = [the five]; }`.
- **Token-handling constraint found in advance:** hermes's rendered
  `config.yaml` lands in the nix store, so the bearer token must NOT go
  through `mcpServers.headers`. The upstream module has an `auth` option
  (tokens stored under `$HERMES_HOME/mcp-tokens/`) — I'll verify its
  shape during the build; fallback is env-var expansion via the dotenv.
  If neither can keep the token out of the store, I stop and we decide
  (tailnet-only exposure without bearer vs. a different injection path).

### Vault conventions
- Read your existing templates/PARA layout first (post-SSH), then add
  templates that match: daily note, GTD inbox capture, meeting-prep,
  flight-debrief. Templates land in the vault via one reviewed write,
  not bulk edits.
- iCloud pinning: disable Optimize Mac Storage for the mini (or Keep
  Downloaded on the vault folder); verification command
  (`find <vault> -name "*.icloud"` must return nothing) in the phase doc.
- **Backup (iCloud is sync, not backup):** launchd daily job on the mini
  rsyncing the vault one-way to the UNAS (same NAS-credential pattern as
  the Kuma backup), versioned by NAS snapshots. The agent has no access
  to the NAS credential or the job.

### Behaviors
- Telegram capture: policy.md already steers writes to Inbox/; the tool
  shape enforces it (`append_inbox` is the only free-text write).
- 05:30 daily note: `hermes cron` entry created via the **CLI on the VM**
  (operator surface — chat cron stays disabled per Phase 0.5), invoking
  create_daily_note + a short brief message. Calendar/tasks sections stay
  placeholder-empty until Phase 4 feeds them.
- Weekly review packet: on-demand prompt using search/list + read tools.
